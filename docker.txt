10: what is docker create.
ans - docker create is used to create a container from an image, but it does not start the container.

This is the main difference:

docker create → Create only
docker run → Create + Start
docker start → Start an existing container

docker create [OPTIONS] IMAGE
docker create --name my-nginx nginx


What happens?

When you run:

docker create --name my-nginx nginx

Docker:

✅ Finds the nginx image (downloads it if needed).
✅ Creates a new container.
❌ Does not start the container.

12: What is Docker build commond.

Great question. docker build is used when you want to create your own Docker image.

You use it when the existing images (like python, nginx, ubuntu) are not enough and you want an image that contains your application.

Why do we use docker build?

Suppose you have a Django project.

my-django-app/
│
├── Dockerfile
├── requirements.txt
├── manage.py
├── myproject/
└── app/

A Dockerfile contains instructions for creating an image.

Example:

FROM python:3.12

WORKDIR /app

COPY . .

RUN pip install -r requirements.txt

CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]

Now build the image:

docker build -t django-app.

After building

Run a container from your image:

docker run -p 8000:8000 django-app

13: What is docker build --no-cache -t myapp .?
ans - if you have created an image and then you have changed in one file all will remain in cache and docker will only rebuild with the new change file
but if we used --no-cache it will rebuild from scratch.

when we use  --no-cahe means rebuld from scratch.
What is cache?

Cache means Docker remembers the result of previous build steps.
Imagine you're building a house.

Without --no-cache
Already built the walls? ✅
Already built the roof? ✅
Only repaint the wall. 🎨

Fast.

With --no-cache
Destroy everything. ❌
Build the walls again.
Build the roof again.
Paint again.

Slow, but everything is fresh.


ans - No problem. Let's understand it with a real Django example.

Suppose your project looks like this:

django-project/
│
├── Dockerfile
├── requirements.txt
├── manage.py
└── myproject/

Your Dockerfile:

FROM python:3.12

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]
First build

Run:

docker build -t myapp .

Docker executes every instruction.

Step 1: FROM python:3.12       ✅
Step 2: WORKDIR /app           ✅
Step 3: COPY requirements.txt  ✅
Step 4: RUN pip install...     ✅
Step 5: COPY . .               ✅
Step 6: CMD                    ✅

Suppose it takes 2 minutes because it installs Django and other packages.

Second build

Now you only change one file:

views.py

Run again:

docker build -t myapp .

Docker thinks:

"I have already done Steps 1–4 before, and nothing changed there. I'll reuse them."

Output (simplified):

Step 1: Using cache ✅
Step 2: Using cache ✅
Step 3: Using cache ✅
Step 4: Using cache ✅
Step 5: Rebuild (because your code changed)
Step 6: Done

This finishes much faster (maybe 10 seconds).

What is cache?

Cache means Docker remembers the result of previous build steps.

Think of it like this:

The first time you cook rice, it takes 20 minutes.
If the rice is already cooked, you don't cook it again—you just use it.

Docker does the same with build steps.

What does --no-cache do?

Now run:

docker build --no-cache -t myapp .

Docker says:

"Ignore everything you remembered. Build everything again."

So it executes:

Step 1: FROM python:3.12
Step 2: WORKDIR /app
Step 3: COPY requirements.txt
Step 4: RUN pip install...
Step 5: COPY . .
Step 6: CMD

Even if nothing changed, it rebuilds every step.

14: docker inspect, logs, info

docker inspect
What does it do?

docker inspect displays detailed information about a Docker object.

It can inspect:

✅ Container
✅ Image
✅ Network
✅ Volume

The output is in JSON format.

Why do we use docker inspect?

Imagine your Django app cannot connect to PostgreSQL.

You can inspect the container to check:

Which image is running?
Which environment variables are set?
Which ports are exposed?
Which volumes are mounted?
Which network is it connected to?

info - docker info is a command that displays information about the Docker Engine running on your machine.

It does not show information about a specific container. Instead, it tells you about the entire Docker environment.

15: Docker Volumes.
Why Do We Need Volumes?

Imagine you have a PostgreSQL container.

docker run --name postgres postgres

Inside the container:

Database
Users
Orders
Products

Now remove the container:

docker rm -f postgres

Everything is gone.

Why?

Because the data was stored inside the container's writable layer, which is deleted along with the container.

docker volume create my-volume


Let's break down this command piece by piece.

docker run -v django-data:/app django-app

Part 1: docker run
docker run
This means:

Create a new container and start it.

Docker now needs an image to create the container.

Part 2: -v
-v

-v stands for volume.

It tells Docker:

"Connect a persistent storage (volume) to this container."

Part 3: django-data
django-data

This is the volume name.

If it doesn't exist, Docker automatically creates it.

You can verify it:

docker volume ls

Output:

DRIVER    VOLUME NAME
local     django-data
Part 4: /app
/app

This is the folder inside the container.

Remember your Dockerfile?

WORKDIR /app

Docker automatically created /app and copied your project there.

Inside the container:

/app
├── manage.py
├── requirements.txt
├── myproject/
└── blog/
Part 5: django-app
django-app

This is the image name.

Docker creates a container from this image.

What happens internally?

Imagine you run:

docker run -v django-data:/app django-app

Docker performs these steps:

Step 1

Creates a new container from the image.

Image
django-app
      │
      ▼
Container
Step 2

Looks for the volume:

django-data

If it doesn't exist:

Docker creates it automatically.
Step 3

Attaches the volume to:

/app

Inside the container.

                     │
